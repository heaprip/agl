# Карта реализации identity/extent killer test

Статус: ограниченная реализация контракта
[`identity-extent-test.md`](identity-extent-test.md). Она не заменяет текущий
evaluator и не объявляет новый calculus.

## Четыре обязательных ответа перед новым механизмом

1. **Объект контракта.** First-class relation occurrence: стабильный
   `EntityId`, неизменяемый `Intension`, отдельные проекции по `Plane`,
   метарёбра и evidence DAG.
2. **Что переиспользуется.** `model::Plane` остаётся контекстом;
   `bank::Ext` остаётся плотным представлением точного конечного отношения;
   `journal::Journal` остаётся append-only историей с проверяемыми ID;
   `model::Strength` остаётся строгостью основания.
3. **Почему старого недостаточно.** `eval::Derivation` ссылается на номер
   строково-канонизированного atom внутри одного `Db` и потому не может быть
   основанием entity/projection/metaedge между контекстами. `Bank` сохраняет
   несколько `Shape` внутри класса, но публично именует класс его extent и не
   даёт конструкции устойчивый ID. `Journal` хранит историю, но не вычисляет
   транзитивную валидность зависимостей.
4. **Сквозная проверка.** `tests/identity_extent.rs`: разные intensions с
   равным extent в `p`, разные endpoints, расхождение в `q`, явное restriction,
   отзыв только пути `a`, сохранение истории, канонический отчёт при
   перестановке входа и двух представлениях exact relation.

## Граница

Модуль не выполняет поиск, не вводит физику, λ-термы, собственный query
planner или новый формат `.agl`. Он хранит результаты существующих или
внешних вычислителей и проверяет, что оптимизация/индексация не стирает четыре
разных объекта: identity, intension, context-indexed extent и evidence.

До прохождения теста API считается экспериментальным. После прохождения
следующее решение — адаптировать к нему `eval::Derivation` и `Bank::Entry` или
отказаться от слоя, а не держать три параллельные модели.
