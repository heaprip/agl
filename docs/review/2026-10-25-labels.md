# Метки вложенности, шаг 1 прототипа H61, 2026-10-25

Критерий объявлен до кода (H61, коммит cc3f310). Здесь вход и выход.

## Вход

- `src/label.rs`: по рёбрам «вид → род» — остовное дерево (род — первый
  по имени), номера в обратном порядке обхода (дети по имени), у узла —
  слитые интервалы его и всех потомков по графу (Agrawal, Borgida,
  Jagadish, SIGMOD 1989 [сверено по DBLP]). «A внутри B» — номер A в
  интервале B. Цикл — ошибка. Метки пока **не связаны с выводом** ядра.
- `tests/label.rs`: случайные графы от seed против замыкания обходом.
- `examples/labels.rs` на рёбрах из `tools/onto_stats.py edges` (ChEBI 200,
  244, 255; WordNet 2021, 2025).
- `examples/census.rs`: сколько атомов казусов приходится на вложенность.

```sh
AGL_SIM_SEEDS=20000 cargo test --release --test label
python3 tools/onto_stats.py edges chebi 255 > target/scratch/chebi255.tsv
cargo run --release --example labels -- target/scratch/chebi255.tsv
```

## Толкование помощника

1. **Метки работают и дёшевы.** Замыкание ChEBI, которое в ядре заняло бы
   5 млн атомов (около 25 ГБ при нынешних 5 КБ на атом), читается из
   462 тыс. интервалов, построенных за 0,2 с.
2. **Сплошной номер — не имя.** Смысл меняется у 1–3 % понятий, а номер —
   почти у всех: любая вставка сдвигает обратный порядок обхода. Это
   подтверждает разделение H61: ссылаться только на неизменное имя, номер
   — пересчитываемое положение.
3. **Промежутки пока не нужны.** Полный пересчёт стоит 0,2 с, поэтому
   метку дешевле построить заново, чем хранить и править. Промежутки
   (или ORDPATH) понадобятся, только если метки будут храниться или
   передаваться между системами.
4. **Для нынешних казусов выигрыша нет**: вложенность там — десятки
   атомов. Выигрыш — на масштабе онтологий (H64).

## Чего шаг не показывает

- Метки не подключены к выводу: ядро по-прежнему выводит `ancestor` и
  `member` правилами. Это шаг 2.
- Рёбра берутся без плоскостей и без отменяемости: у ядра рёбра могут
  быть разными в разных плоскостях и могут быть отменены. Как строить
  метки по плоскостям — вопрос шага 2.
- Одна ось (род). Вторая ось (роли, «часть чего») не размечалась.
- Цепочка вывода «почему A внутри B» из метки не читается; её придётся
  восстанавливать по рёбрам.

## Шаг 2а: `nesting` в ядре

Критерий объявлен до кода (H61, коммит b2368af). Автор выбрал: метки
строятся заново в каждой плоскости из видимых в ней рёбер.

- `nesting ID: N(a, b) by E(x, y)` разворачивается при разборе в два
  строгих правила `ID_base` и `ID_step`; понятия, рефлексия, обучение
  видят обычные правила. Вывод не крутит их по кругу: после правил своего
  слоя он строит метки по рёбрам и выдаёт атомы N с теми же выводами, что
  дали бы правила, и повторяет, если правила слоя добавили рёбра.
- Метки теперь принимают циклы: компоненты сильной связности (Тарьян),
  внутри компоненты все вложены друг в друга. Шаг 1 считал цикл ошибкой —
  это снято, иначе `forbid own_ancestor` в родстве перестал бы работать.
- Атомы N из фактов и других правил — последний шаг пути (ребро к
  «свежей копии» рода без выходящих рёбер).
- Если атом N проиграл спор и заблокирован — эта вложенность в этом
  контексте выводится правилами, как раньше.

| Критерий | Итог |
| --- | --- |
| (а) 20 000 случайных программ: отчёт и все замыкания (атомы, выводы, посылки, строгость, доверие, споры) с `nesting` побайтно равны версии с двумя правилами | да; метками выведено 6844 замыкания из 7056 (97 %), правилами — 212, где атом N проиграл спор |
| (б) `cases/kinship.agl` через `nesting` | да |
| (в) sim (20 000), oracle (50 000), все тесты, clippy | да |

От противного: тест падает, если `nest` ничего не добавляет; если
забыть данные атомы N как посылки; если пускать к «свежей копии» без
ребра.

Цепочка из 400 звеньев (80 тыс. атомов N), `target/release/agl`:

| | время | пик памяти |
| --- | --- | --- |
| два правила | 33,6 с | 713 МБ |
| `nesting` | 9,3 с | 152 МБ |

Атомов столько же; память падает, потому что правилам нужно 400 кругов,
и на каждом перестраивается индекс. Оставшиеся 9 с — разбор доверия и
споров по посылкам (`settle`, `decide`), он от меток не зависит.

**Не показывает:** экономии атомов (все атомы N создаются) — это шаг 2б;
`--where`, `--concepts` и остальные модули не проверялись на `nesting`
отдельно (они видят те же два правила).

## Шаг 2б: ленивые атомы

Объявлено до кода (H61, коммит c1f6a87). `nesting ... lazy`: атом N(x, y)
создаётся, только когда его спрашивает тело правила, вместе с «конусом» —
всеми N(z, y) на путях от x к y, — с выводами шага 2а. Ленивость явная:
модули вне вывода (`--where`, обучение, рефлексия) иначе молча увидели бы
неполное замыкание. Ядро проверяет условия и при их нарушении строит
замыкание целиком: N читают только тела правил (не запросы, запреты,
единственность, сравнения, агрегаты), нет отрицаний N, рёбра — факты.

| Критерий | Итог |
| --- | --- |
| (а) 20 000 программ, где N читают только правила: отчёт побайтно равен 2а; созданные атомы равны атомам 2а | да; создано 236 891 атом N против 377 912 |
| (б) программы, где N читают запросы, — как в 2а | да (прежние тесты `nesting` и `seminaive`) |
| (в) замер на настоящих данных | ниже |

От противного: тест падает, если создавать только спрошенный атом без
конуса.

```sh

cargo run --release -- target/scratch/wn_lazy.agl
```

(да) и 10 без вложенности (неизвестно: мир ядра открыт):

| | `lazy` | целиком (2а) |
| --- | --- | --- |
| верных ответов | 30 из 30 | 10 из 30 |
| атомов замыкания | 104 | обрыв на 100 000 (нужно 742 396) |
| время | 0,7 с | 8,4 с |
| пик памяти | 254 МБ | 1,5 ГБ |

Ответы верны только потому, что нужный вывод сложился на первом круге.
Дальше — шаг 3 (сущность = номер: память фактов, около 2,9 КБ на атом) и

## Шаг 3б: атом = номер

Объявлено до кода (H61). Сделано в `src/eval.rs`:

- **`Db`** — атомы с выводами в массиве; номер атома (`Id`) — его место.
  Ключ (напечатанный атом) хранится один раз и служит упорядоченным
  указателем «текст → номер»: два атома — один, если печатаются одинаково,
  как и раньше. Обход для вывода идёт по ключам.
- **Посылки** — номера (`Box<[Id]>`), упорядоченные по тексту ключа; текст —
  `Db::key`, `Db::premise_keys`. Запись «∅ …» (агрегат ничего не нашёл) —
  номер из отдельного диапазона.
- **`decide`, `settle`, `founded`** — массивы по номерам вместо словарей по
  строкам; дополнение атома ищется один раз на решение.
- **Полунаивный вывод**: дельта и индекс сопоставления — номера; ключи
  индекса — общие имена (`Name`), без новых строк на каждый раунд. Пока
  сопоставление держит базу на чтение, посылка — номер или ключ ещё не
  созданного ленивого атома; номер ей даёт конец раунда, после конусов.
- **`Lazy`**: узлы — номера меток (`Labels::node`, `name_at`), рёбра и
  атомы N «извне» — номера атомов, отсортированные по узлу (CSR); строк на
  ребро больше нет.

| Критерий | Итог |
| --- | --- |
| 20 000 программ sim: отчёт и все замыкания с выводами (посылки — текстом) побайтно равны бинарнику 1b65a95 | да |
| 53 файла `cases/` × 6 режимов, `--learn`, `--where`; WordNet и цепочки 2а с `-v` и без | да, без расхождений |
| oracle (50 000), sim и nesting (по 20 000), все тесты | зелёные |
| от противного: посылки по номеру, а не по тексту | ловится: другой хеш sim, 39 казусов расходятся под `-v` |

Замер на WordNet (`examples/memstage.rs`: счётчик-аллокатор — куча и её
пик; `/usr/bin/time -l` — резидентный пик):

| | до шага 3 | 3а | 3б |
| --- | --- | --- | --- |
| пик кучи, вывод | 184,5 МБ | 161,6 МБ | **111,7 МБ** |
| куча в конце (программа + замыкание) | 107,0 МБ | 84,9 МБ | 64,5 МБ |
| выделений памяти | 7,65 млн | 6,26 млн | 2,55 млн |
| резидентный пик, вывод | 249 МБ | 226 МБ | 157 МБ |
| время вывода | 0,65 с | 0,70 с | 0,39 с |

По этапам после 3б (куча после этапа; в скобках — до 3б): программа 29,5;

Толкование помощника:

1. Выигрыш 3б больше, чем 3а, и шире памяти: время вывода WordNet упало на
   40 %, Гамильтона — на 30 %, широкий sim — с 7,4 до 4,7 с. Строки-ключи
   стоили не только места: каждая проверка «вывод уже есть?» и каждый шаг
   `decide` сравнивали тексты.
2. Пик теперь — построение меток в `Lazy` (временно +31 МБ сверх

3. На атом в базе осталось около 415 Б: атом с аргументами, один вывод,
   ключ-текст и его узел в индексе. Указатель без текста (по строению атома,
   а не по печати) — возможный шаг 3в; он требует доказать, что строение и
   печать различают атомы одинаково (числа: `0` и `-0`).

## Шаг 7: ChEBI целиком в ядре, два выпуска — две плоскости

Объявлено до кода (H61). `tools/onto_stats.py releases chebi 244 255`
пишет программу: ось `release`, значения `r244` и `r255` внутри `chebi`;
ребро обоих выпусков — факт в `release:chebi` (283 718), только 244 —
в `r244` (434), только 255 — в `r255` (16 105); `nesting ... lazy`. Вопросы
от seed 1: по 10 пар «вид — предок» в обоих выпусках, только в 244, только
в 255 и ни в одном, каждая — в обеих плоскостях.

```sh
python3 tools/onto_stats.py releases chebi 244 255 > target/scratch/chebi2.agl
cargo run --release -- -v target/scratch/chebi2.agl
```

Предел замыкания `MAX_ATOMS` по описанию ограничивал выведенные атомы, а
считал и факты; теперь — 100 000 сверх фактов контекста (число то же).
Тест `closure_limit_counts_derived_atoms_only` (`tests/nesting.rs`): 100 001
факт — без обрыва, 160 000 выведенных — обрыв; падает, если предел снова
считает факты.

| Критерий | Итог |
| --- | --- |
| (а) 80 ответов верны, обрыва нет | да, 80 из 80 |
| (б) объяснение «да» — цепочка рёбер своей плоскости или общих | да: например, в `r244` первое звено — `e172758 @ release:r244`, три других — `@ release:chebi`; в `r255` того же ребра нет, ответ `unknown` |
| (в) время и пик (`time -l`) | 4,3 с, 1,59 ГБ; ожидание — меньше 15 с и 1–3 ГБ |
| (г) отчёты 53 казусов в 6 режимах и 20 000 программ sim побайтно прежние; oracle 50 000, sim и nesting по 20 000, все тесты | да |

Толкование помощника:

1. Плоскости на масштабе работают так же, как на казусах: одно и то же
   «X — вид Y» верно в одном выпуске и неизвестно в другом, и объяснение
   показывает, каким ребром какой плоскости это держится.
2. Память — 1,59 ГБ на четыре контекста (`{}`, `chebi`, `r244`, `r255`);
   из чего она складывается, не разбиралось. Каждый контекст держит свою
   копию 300 тыс. фактов и свои метки — это и есть «метки в каждой
   плоскости заново» (выбор автора к шагу 2); «одни метки + исключения»
   (шаг 6) сократил бы именно это.
3. Не показывает: отрицаний и споров в ChEBI нет, поэтому разбор доверия на
   масштабе не нагружен; вторая ось (`has_role`) — шаг 4.

## Шаг 4: две оси — строение и роль

Объявлено до кода (H61). ChEBI 255: химические термины и роли — две
непересекающиеся иерархии (1 649 ролей, 1 874 ребра `is_a` между ними;
59 114 рёбер `has_role`, все от химии к роли). Роль наследуется вниз по
строению и вверх по ролям; всех пар «термин — роль» 541 334.

```sh
python3 tools/onto_stats.py axes 255 > target/scratch/axes.agl       # две вложенности
python3 tools/onto_stats.py axes 255 one > target/scratch/axes1.agl  # одна на обе иерархии
cargo run --release -- -v target/scratch/axes.agl
```

Запись — две вложенности (`kind_of` по `is_a`, `role_kind` по
`role_is_a`) и четыре правила: роль своя, унаследована по строению,
расширена по ролям, то и другое. 50 вопросов от seed 1 — по 10 каждого вида
и 10 без роли.

| Критерий | Итог |
| --- | --- |
| (а) 50 из 50, обрыва нет | да, в обеих записях |
| (б) объяснение «то и другое» проходит обе оси | да: Val-Tyr-Tyr → трипептид → олигопептид → пептид → органическое аминосоединение (`has_role` основание Брёнстеда) → акцептор → химическая роль |
| (в) атомов, время, пик | 40 ответов, 4 576 атомов `kind_of` и 45 `role_kind` против 541 334 пар и 5 млн атомов замыкания; 2,3 с, 531 МБ |
| (г) одна вложенность на обе иерархии | те же 50 ответов; 4 621 атом, 1,6 с, 529 МБ |
| (д) ядро не трогать | **не сбылось**: см. ниже |

**Что пришлось изменить.** Первый прогон дал верные ответы за 44 с. Время
уходило на конусы ленивой вложенности: `cone(x, y)` перебирал всё, что
внутри y, а для корня ChEBI это вся онтология — и так для каждого предка
каждого вопроса. Теперь конус берётся из предков x (их десятки), с той же
проверкой; множество то же, поэтому замыкание то же. 44 → 2,3 с.
Проверка: отчёты 53 казусов в 6 режимах, 20 000 программ sim, ChEBI шага 7
(с `-v`) и WordNet побайтно прежние; nesting и sim по 20 000, oracle 50 000,
все тесты зелёные; тест ленивости падает, если из конуса выпадает ветка

Толкование помощника:

1. **Оси складываются из того, что есть**: вложенность на каждую ось и
   правила, которые их связывают. Нового механизма «вектор» в ядре не
   понадобилось; точка с двумя координатами — это пара меток, а
   наследование роли — правило над ними.
2. **Разделение осей ответов не меняет** (г): в ChEBI иерархии ролей и
   строения не пересекаются, и одни метки на обе работают так же. Оси
   различаются смыслом связи (`has_role`), а не устройством меток.
3. **Ленивость зависит от порядка посылок.** Атом вложенности создаётся,
   когда метка дала пару, даже если остальное тело не совпало. В правиле
   «предок x, у которого роль r» с предком впереди создаётся 4 576 атомов
   `kind_of`, с ролью впереди — 41. Ответы те же. Возможная поправка —
   создавать атомы только для совпавших тел; не делалась.
4. Не показывает: сумму координат («родитель + женщина = мать») — это
   шаг 5, понятие = область; оси, которых нет в данных (их надо вывести).
