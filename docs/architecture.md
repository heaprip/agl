# Вычислительное ядро: рабочий контракт

Статус: рабочая спецификация после аудита 2026-10-25, не решение автора и не
описание уже готового кода. Она нужна как граница для следующих реализаций:
новый вычислитель не считается частью agl, пока не проходит этот контракт.

Рабочее проектное название конструкции — **контекстно-индексированный
открытый типизированный метаграф с provenance**. После академического аудита
это следует читать как контракт данных, а не как уже установленный новый
формализм. Ближайшее основание вычислительного фрагмента — graphical regular
logic / relational calculus; открытые гиперграфы дают композицию интерфейсов,
а HiLog/F-logic, provenance и ATMS — отдельные соседние механизмы. Настоящая
indexed/presheaf semantics появится только после определения reindexing и
проверки её законов. «Плоскостно-осевой гиперграф» остаётся коротким проектным
именем, не академическим термином.

## 0. Словарь из смежных теорий

| Проектное слово | Рабочий академический термин | Причина |
| --- | --- | --- |
| гиперграф, где ребро бывает концом ребра | directed typed **metagraph** | обычный гиперграф разрешает ребру соединять вершины; метаграф разрешает целую связь как target |
| структурная ось | **port**; набор открытых концов — boundary/interface | открытые типизированные гиперграфы и string diagrams |
| склейка по осям | composition of open systems, формально pushout/cospan composition | интерфейсы отождествляются, внутренняя структура сохраняется |
| плоскость | **context** в базовом частичном порядке | контексты уточняются и пересекаются |
| значение в плоскости | context-indexed extent; кандидат на fiber/section | данные индексированы контекстом, functor laws ещё не доказаны |
| переход в более узкую плоскость | кандидат на restriction/reindexing | так называть операцию строго можно только после проверки identity/composition laws |
| путь построения отношения | **intension** или presentation | задаёт, как отношение построено |
| точный набор кортежей в плоскости | **extension/extent** | денотация intension в конкретном контексте |
| забыть внутренность, оставить наблюдаемое отношение | **black-boxing** | семантика открытой системы на её интерфейсе |
| основание результата | derivation; совокупность путей — provenance/lineage | результат остаётся proof-relevant |

Поэтому слово «ось» дальше зарезервировано для координаты контекстного
пространства. Свободный конец отношения называется портом. Если позднее
окажется, что контекстная ось сама выводится из сгруппированных портов, это
будет явной конструкцией, а не терминологическим совпадением.

## 1. Три структуры, которые нельзя смешивать

1. **Типизированный метаграф** хранит сущности и отношения с именованными
   ролями. Отношение имеет собственную идентичность. Построенное отношение
   может быть target отношения следующего уровня — это метаребро.
2. **Контекстное пространство** состоит из осей условий. Значения одной оси
   образуют порядок уточнения; плоскость выбирает область в произведении
   осей. Она отвечает на вопрос «где это видно или верно».
3. **Граф оснований** хранит, почему результат получен: операцию построения,
   исходные сущности, плоскость, посылки и строгость основания.

Внутри одной вычислительной конструкции открытые концы называются **портами**,
а выбранный набор портов — её **интерфейсом**. Контекстная ось — координата,
значение которой ограничивает плоскость.

## 2. Минимальные объекты

Пусть `EntityId` — стабильная идентичность сущности, а `Plane` — конечное
ограничение по контекстным осям.

`Intension` — неизменяемый граф построения (presentation):

- `Primitive(source)` — исходная сущность;
- `Glue(parts, identifications, interface)` — склейка портов;
- `Hide(part, ports)` — забывание внутренних портов (существование);
- `Reify(part, boundary)` — склейка становится сущностью и потому может быть
  концом следующего гиперребра;
- `Restrict(part, context)` — только наблюдение в области, не новая сущность.

Запись сущности обязана хранить как минимум:

```text
Entity {
    id: EntityId,
    intension: Intension,
    bases: [EvidenceId],
}
```

Основания образуют двудольный AND/OR-граф, уже неявно присутствовавший в
`eval::Db`: proposition/`ClaimId` — OR-узел с несколькими альтернативными
доказательствами, а одна запись `Evidence` — AND-узел, которому нужны все
premise claims. Хранить в premise один выбранный `EvidenceId` было бы ошибкой:
это размножило бы декартово произведение путей и ломало бы альтернативную
поддержку при отзыве.

```text
Evidence {
    id: EvidenceId,
    conclusion: ClaimId,
    premises: [ClaimId],
    context: Plane,         # где вычислен вывод
    source_context: Plane,  # где объявлен источник/правило
    operation,
    strength,
}
```

Проекция вычисляется отдельно:

```text
extent(entity, context) -> ExactRelation
```

`ExactRelation` — точное конечное множество кортежей. Плотный битовый вектор,
разреженный отсортированный вектор и индекс — представления одного интерфейса,
а не разные семантики.

Главный инвариант:

```text
extent(a, p) = extent(b, p)  не влечёт  a = b.
```

Совпадение проекций создаёт утверждение с основанием
`EqualAt(a, b, p, evidence)`. Оно не объединяет идентичности и не стирает пути
построения.

## 3. Один вычислительный шаг

Вход шага — цель, плоскость и уже построенный метаграф. Шаг состоит из пяти
явных фаз:

1. выбрать видимую в контексте часть метаграфа;
2. состыковать порты существующих сущностей одной операцией
   `Glue`;
3. создать новую сущность с новым `EntityId` и сохранить граф построения;
4. вычислить её проекцию на текущую плоскость множеством за раз;
5. сохранить основание результата и, если сравнивались проекции, отдельный
   закон о совпадении или вложении.

После фазы 3 результат уже может быть участником следующего метаребра. Фаза
4 не создаёт его идентичность, а только даёт наблюдаемый вид.

Схематически:

```text
(metagraph, context, goal)
    -> visible subgraph
    -> Glue / Hide / Reify
    -> entity + intension
    -> extent(entity, context)
    -> evidence + local laws
    -> next hyperedge
```

Это и есть предполагаемое вычисление через плоскостно-осевой гиперграф:
вычислительный поток идёт по композиции открытых интерфейсов, область
истинности задаётся контекстом-плоскостью, а промежуточные склейки остаются
сущностями метаграфа. Вычисление extent — его локальный black-boxing, а не
подмена внутренней сущности внешним поведением.

## 4. Закон между плоскостями

Результат всегда локален: `extent @ context on evidence`. Равенство,
вложение и функциональность — свойства extensions или intensions с указанным
основанием, а не встроенные имена операций.

- Равенство запросов по гомоморфизмам в обе стороны — строгое основание.
- Совпадение точных конечных проекций — основание мира в данной плоскости.
- Перенос совпадения на более широкую область — отменяемое обобщение.
- Плоскость, где проекции расходятся, — опровергатель этого обобщения, а не
  уничтожение одной из сущностей.

Независимость оснований пока не формализована. Равенство чисел моделей или
повтор одного алгоритма независимым основанием не считается.

## 5. Связь с лямбда-исчислением

Лямбда-исчисление остаётся внешней звездой для проверки, а не языком ядра:

- связывание концов соответствует склейке портов;
- квантор существования — `Hide`;
- абстракция — `Reify` конструкции с границей;
- применение — одна из возможных склеек, функциональность которой надо
  вывести;
- β-редукция — проверочный закон для выбранного перевода, не стратегия
  поиска ядра.

Поэтому тесты с K, S и β могут опровергнуть реализацию, но не имеют права
задавать её внутренние операции.

## 6. Обязательный сквозной тест

До следующего большого поиска нужен малый мир, где:

1. две разные intensions `a` и `b` имеют равные extensions в плоскости `p`;
2. `a.id != b.id`, оба пути построения и оба основания сохранены;
3. `a` и `b` независимо используются как концы метаребра;
4. в уточнённой или расширенной плоскости `q` их проекции расходятся;
5. ядро показывает `EqualAt(a,b,p)` и исключение при `q`, не переписывая
   историю и не склеивая сущности.

Без этого теста relation-first остаётся декларацией: вычислитель снова может
незаметно заменить сущность её объёмом.

Полный формат теста, fixtures, обязательные assertions и уровни приёмки — в
[`impl/identity-extent-test.md`](impl/identity-extent-test.md).

## 7. Соответствие текущему коду

| Часть контракта | Что уже есть | Чего не хватает |
| --- | --- | --- |
| метаребро с ролями | `meta::Metaedge` принимает `EntityId` отношения и endpoints | ссылка на relation occurrence в `.agl` и обычном query path |
| контекстная плоскость | `model::Plane`; отдельные `Projection.context`, `Evidence.context/source_context` | формальные restriction maps в общем API |
| путь построения | общий `meta::Intension`; его создают `eval::Derivation`, `bank::Entry`; `layer::Query::intension` даёт ту же открытую структуру | перенос остальных отдельных исполнителей |
| точная проекция | `bank::Ext`, общий `bits::DenseSet`, A3 | единый интерфейс плотного и разреженного вида |
| логика склеек | `Bank::Entry` несёт `Entity + construction Evidence + Projection`; `layer` сохраняет все IDs при равном extent | evidence/projection для результатов следующего слоя |
| граф оснований | общий AND/OR-carrier `ClaimId/Evidence`; `Derivation` использует его напрямую | journal/replay и политика независимости оснований |
| локальные исключения | `EqualAt`, `Metagraph` с сохранением истории | типизированный контрпример в отчёте и DSL |

Первый уровень `tests/identity_extent.rs` теперь строит обе intensions реальным
`Bank`, проводит их через общий carrier и использует как endpoints. Это ещё не
означает завершение миграции: DSL-ссылки, сериализация/replay и
плотное/разреженное представления остаются следующими барьерами.

## 8. Предохранитель от второго калькулятора

До написания нового механизма надо заполнить четыре строки:

1. какой объект контракта он реализует;
2. какой существующий тип или алгоритм переиспользует;
3. почему существующего механизма недостаточно, если вводится новый;
4. какой сквозной тест связывает его с `Plane`, `Intension` и `Evidence`.

Если ответов нет, код остаётся внешним экспериментом или звездой и не
считается развитием ядра.

## 9. Академические опоры и границы переноса

- Fong, Spivak, [Graphical Regular
  Logic](https://arxiv.org/abs/1812.05765), и Carboni, Walters,
  [Cartesian Bicategories I](https://doi.org/10.1016/0022-4049(87)90121-6):
  основная семантика положительных запросов-склеек, копирования, удаления и
  существования. Это ближе к вычислительному ядру, чем простое соседство
  метаграфа, cospans и предпучка.
- Chen, Kifer, Warren, [HiLog](https://doi.org/10.1016/0743-1066(93)90039-J),
  и Kifer, Lausen, Wu, [F-logic](https://doi.org/10.1145/210332.210335):
  отношения и формулы как данные и higher-order syntax уже имеют first-order
  semantics. `Reify` не даёт λ-abstraction или β-семантику автоматически.
- Kifer, Swift, [ErgoAI](https://arxiv.org/abs/2603.29819): обязательный
  baseline для сочетания F-logic, HiLog, well-founded semantics,
  defeasibility и updates; готового open-hypergraph/context/provenance
  контракта там нет.

- Bonchi, Gadducci, Kissinger, Sobociński, Zanasi, [String Diagram Rewrite
  Theory I](https://arxiv.org/abs/2012.01847): типизированные гиперрёбра с
  упорядоченными входами/выходами, interfaces и DPO-переписывание. Отсюда
  берутся `port`, `interface` и комбинаторное представление синтаксиса.
- Baez, Courser, [Structured Cospans](https://arxiv.org/abs/1911.04630):
  открытые системы с входом и выходом, композиция по общей границе. Отсюда
  берётся принцип, что склейка должна быть общей операцией композиции.
- Goertzel, [Folding and Unfolding on
  Metagraphs](https://arxiv.org/abs/2012.01759): targets типизированного
  метаграфа могут указывать на целые links. Это точное основание для
  метарёбер; отражающее переписывание MeTTa из этого не заимствуется.
- Fong, Sarazola, [A Recipe for Black Box
  Functors](https://arxiv.org/abs/1812.03601): внешнее наблюдаемое поведение
  отделяется от внутренней сети композиционным отображением. Отсюда берётся
  граница между `Intension` и `extent`.
- Curry, [Sheaves, Cosheaves and
  Applications](https://arxiv.org/abs/1303.3255), и Robinson, [Sheaves are
  the canonical datastructure for sensor
  integration](https://arxiv.org/abs/1603.01446): данные над частями базы и
  restriction maps. Это только кандидат на семантику плоскостей: сначала
  требуется определить context category и доказать functorial restriction;
  затем отдельно проверять sheaf condition. Defeasible closure сама по себе
  этих законов не даёт.
- Abramsky, Brandenburger, [The Sheaf-Theoretic Structure of Non-Locality
  and Contextuality](https://arxiv.org/abs/1102.0264): совместимые локальные
  данные могут не иметь глобальной склейки. Это эталон для различения
  локального совпадения и глобального тождества.
- Grädel, Tannen, [Semiring Provenance for First-Order Model
  Checking](https://arxiv.org/abs/1712.01980): provenance отражает зависимость
  результата от атомарных фактов, включая работу с отрицанием. Семиринги не
  принимаются как готовая модель отменяемого вывода; пока сохраняется полный
  derivation DAG.

Ни одна из этих работ по отдельности не является теорией agl. В частности,
обычный открытый гиперграф не даёт link-to-link, метаграф сам по себе не даёт
контекстных restriction maps, а предпучок не задаёт отменяемый вывод.
